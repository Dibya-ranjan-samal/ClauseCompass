# 08 — BM25, from TF-IDF Up

A 1994 algorithm that still beats neural retrieval on some queries. Understanding
*which* queries, and why, is the point.

---

## 1. What it is

**BM25** ("Best Match 25") scores a document against a query by weighted
term overlap. It is a **sparse** retriever: conceptually one dimension per
vocabulary word, almost all zero.

No neural network, no training, no embeddings. Just counting, with two good
corrections.

## 2. Why it exists alongside dense retrieval

Module 06 named dense retrieval's weakness: it blurs proper nouns and rare terms.
Concretely, from this project's own eval questions:

> *"Under the **Adams Golf** Endorsement agreement, which state's law governs it?"*

To an embedding model, "Adams Golf" and "Bravatek Solutions" are nearly the same
thing — both are company-shaped entities in the same syntactic slot. Nothing in
contrastive training rewards separating them.

To BM25, they are **different tokens**. `adams` either appears in the document or
it doesn't. That is not a subtlety it can get wrong.

**The complementarity, stated precisely:**

| | Dense | BM25 |
|---|---|---|
| "how do we end this early" → *Termination for Convenience* | ✅ finds it | ❌ no shared terms |
| "Adams Golf" → the Adams Golf contract | ❌ blurs entities | ✅ exact token |

Neither dominates. That is the entire argument for hybrid retrieval (module 09).

## 3. Building it up: TF → TF-IDF → BM25

### Level 1: raw term frequency

"Score a document by how often the query terms appear."

```
score(D, Q) = Σ_{q ∈ Q} count(q, D)
```

Two immediate problems:

1. **Common words dominate.** "the" appears everywhere, contributing nothing.
2. **Long documents win by size.** A 50,000-word contract contains more of
   everything.

### Level 2: TF-IDF — down-weight common terms

Add **inverse document frequency**: rare terms are informative, common terms are
not.

```
              N
IDF(q) = log ────
             n(q)
```

- `N` — total documents (here, chunks: 18,280)
- `n(q)` — how many contain term `q`

Work it: `"the"` appears in ~18,000 of 18,280 chunks → `log(18280/18000) = 0.015`,
essentially nothing. `"indemnification"` appears in perhaps 400 → `log(18280/400)
= 3.82`, over 250× the weight.

**IDF is where the intelligence lives.** No training, no supervision — the corpus
statistics tell you which words matter.

BM25 uses a smoothed variant that avoids division by zero and negative weights:

```
             ⎛  N − n(q) + 0.5      ⎞
IDF(q) = ln ⎜ ───────────────── + 1 ⎟
             ⎝   n(q) + 0.5         ⎠
```

### Level 3: BM25 adds two corrections

TF-IDF still has two flaws. BM25 fixes both.

```
                        f(q,D) · (k₁ + 1)
score(D,Q) = Σ IDF(q) · ─────────────────────────────────────
              q∈Q        f(q,D) + k₁ · (1 − b + b · |D|/avgdl)
```

| Symbol | Meaning | Typical |
|---|---|---|
| `f(q,D)` | count of term `q` in document `D` | — |
| `\|D\|` | length of `D` in tokens | — |
| `avgdl` | average document length in the corpus | — |
| `k₁` | **saturation** control | 1.2–2.0 |
| `b` | **length-normalisation** control | 0.75 |

#### Correction 1 — saturation (`k₁`)

Is a document with 20 mentions of "indemnification" twice as relevant as one with
10? No. After a few mentions, the document is clearly *about* the topic; further
mentions add little.

Look at the shape. Ignoring length for a moment, the TF factor is:

```
f · (k₁+1) / (f + k₁)
```

With `k₁ = 1.2`:

| `f` | TF factor | marginal gain |
|---|---|---|
| 1 | 1.00 | — |
| 2 | 1.38 | +0.38 |
| 3 | 1.57 | +0.19 |
| 5 | 1.77 | +0.10 |
| 10 | 1.96 | +0.04 |
| 100 | 2.17 | ~0 |

It **saturates** toward `k₁+1 = 2.2`. Raw TF would have given 100 for `f=100`.

Notice `k₁` controls *how fast*: `k₁ → 0` makes it binary (present or not);
large `k₁` approaches linear TF.

#### Correction 2 — length normalisation (`b`)

A long document contains more of every term by chance. The denominator's
`(1 − b + b·|D|/avgdl)` factor penalises length:

- `b = 0` → no normalisation
- `b = 1` → full normalisation, divide by relative length
- `b = 0.75` → the usual compromise

For a document twice the average (`|D|/avgdl = 2`) with `b = 0.75`:
`1 − 0.75 + 0.75·2 = 1.75`. The denominator grows, the score shrinks.

### A worked example, end to end

Corpus: 1,000 chunks, `avgdl = 200` tokens. Query: `"force majeure"`.

- `force` appears in 150 chunks; `majeure` in 40.
- Chunk D: 250 tokens, contains `force` 3×, `majeure` 2×.
- `k₁ = 1.2`, `b = 0.75`.

**IDF:**
```
IDF(force)   = ln((1000 − 150 + 0.5)/(150 + 0.5) + 1) = ln(5.65 + 1)  = 1.89
IDF(majeure) = ln((1000 −  40 + 0.5)/( 40 + 0.5) + 1) = ln(23.7 + 1)  = 3.21
```
`majeure` is rarer, so worth ~1.7× more. Correct — it's the discriminating term.

**Length factor:** `1 − 0.75 + 0.75·(250/200) = 0.25 + 0.9375 = 1.1875`
So `k₁ · 1.1875 = 1.425`.

**TF components:**
```
force:   3·(2.2) / (3 + 1.425) = 6.6 / 4.425 = 1.49
majeure: 2·(2.2) / (2 + 1.425) = 4.4 / 3.425 = 1.28
```

**Total:** `1.89 · 1.49 + 3.21 · 1.28 = 2.82 + 4.11 = ` **6.93**

Now note the scale: **6.93**. Cosine similarity lives in [0,1]. BM25 is
unbounded and corpus-dependent. **These two numbers cannot be averaged.** That is
module 09's entire problem.

## 4. Tokenisation is a design decision, not a detail

```python
TOKEN = re.compile(r"[a-z0-9]+(?:-[a-z0-9]+)*")

def tokenize(text: str) -> list[str]:
    return TOKEN.findall(text.lower())
```

That pattern keeps hyphenated compounds **intact**: `non-compete` is one token,
not two. For legal text that seems obviously right — `non-compete`,
`most-favoured-nation`, `arm's-length` are single concepts.

**Measured, it is a genuine two-edged trade:**

| Query | Top BM25 score | Why |
|---|---|---|
| `force majeure` | **13.85** | matches a real *Force Majeure* section |
| `indemnification` | 7.04 | matches indemnification clauses |
| `non-compete` | 7.77 ✅ | contracts write it hyphenated |
| `most-favored-nation` | **0.00** ❌ | one token, appears nowhere in the corpus |
| `most favored nation` | **22.79** ✅ | contracts write it *unhyphenated* |

A hyphenated query term absent from the corpus scores **exactly zero**. BM25 has
no partial credit — there is no notion of "close to a token".

**Detecting this class of bug:** run exact-term probe queries whose answers you
know must exist and assert the top hit literally contains the term. Two lines,
and it catches tokenisation regressions immediately.

**The fix (not applied here, deliberately):** emit both the compound and its
parts. It was recorded rather than fixed because no scored eval question depended
on it — the one aggregation question mentioning MFN has no gold chunks. Knowing
*why you didn't fix something* is part of engineering judgement.

## 5. Implementation

```python
class BM25Retriever:
    CACHE = Path("data/interim/bm25.pkl")

    def __init__(self, chunks_path="data/interim/chunks_enriched.json"):
        if self.CACHE.exists():
            with self.CACHE.open("rb") as f:
                self.bm25, self.rows = pickle.load(f)
        else:
            chunks = json.loads(Path(chunks_path).read_text())
            # Cache only what retrieval needs - full payloads would put
            # hundreds of MB in memory on an 8 GB machine for no benefit.
            self.rows = [(c["chunk_id"], c["doc_id"], c["text"]) for c in chunks]
            self.bm25 = BM25Okapi([tokenize(t) for _, _, t in self.rows])
            ...

    def search(self, query, k, doc_id=None):
        scores = self.bm25.get_scores(tokenize(query))   # O(n) over all chunks
        idx = np.asarray(self.by_doc.get(doc_id, [])) if doc_id else None
        if idx is not None:
            order = idx[np.argsort(-scores[idx])][:k]     # restrict, then rank
        else:
            order = np.argsort(-scores)[:k]
        ...
```

Notes:

- **`get_scores` is O(n)** over all 18,280 chunks. `rank_bm25` scores everything;
  a production inverted index would only touch documents containing a query term.
  Fine at this scale (58 ms p95), wrong at 10M.
- **Doc filtering is done by index restriction**, mirroring module 07's
  pre-filtering: score all, then rank only the target document's rows.
- **The cache stores three fields, not whole payloads** — a deliberate memory
  decision on an 8 GB machine.

## 6. In this system — and the expectation that failed

| Scope | recall@5 | recall@50 | MRR | p95 |
|---|---|---|---|---|
| corpus-wide | 0.2229 | 0.5467 | 0.207 | 58 ms |
| doc-scoped | 0.4107 | 0.9801 | 0.3186 | 56 ms |

BM25 **loses to dense overall** (0.363 / 0.575), which is expected.

### The prediction that was wrong

The Day 4 brief predicts BM25 will beat dense on **near-miss** questions — where
a legally adjacent clause is the plausible wrong answer. Measured:

| Type | dense | BM25 | verdict |
|---|---|---|---|
| near_miss, corpus-wide | 0.333 | **0.250** | BM25 **lost** |
| near_miss, doc-scoped | 0.500 | **0.250** | BM25 **lost** |

**Why, in hindsight:** a near-miss trap is *legally adjacent language*. "Cap on
liability" and "uncapped liability" share almost all their vocabulary — `liability`,
`shall`, `exceed`, `damages`. Lexical overlap is precisely what cannot separate
near-synonyms. Asking BM25 to distinguish them is asking it to do the one thing
it structurally cannot.

**What did solve near-miss: the cross-encoder, at 0.917** (module 10). Because it
reads query and clause *jointly* and can tell "capped at $X" from "uncapped for
gross negligence".

This is a good example of a hypothesis that sounded right, was tested, and failed
— and where the failure taught you the mechanism.

## 7. Failure modes

| Failure | Symptom | Detect | Fix |
|---|---|---|---|
| Tokeniser splits compounds | `non-compete` matches nothing useful | probe known terms, assert literal match | keep hyphens |
| Tokeniser keeps compounds | unhyphenated variant scores 0.00 | probe both spellings | index compound **and** parts |
| Case sensitivity | `Indemnification` ≠ `indemnification` | probe with mixed case | `.lower()` in the tokeniser |
| Stale pickle cache | results reflect an old corpus | store a corpus hash in the cache | invalidate on chunk change |
| No stopword handling | fine — IDF already handles it | — | don't bother; IDF is the mechanism |
| Memory blowup | swap thrash on a small machine | measure the pickle size | cache only needed fields |
| Vocabulary mismatch | query terms absent → all scores 0 | check for an all-zero score vector | fall back to dense; hybrid |

The all-zero case deserves attention: if no query term appears anywhere, **every
score is 0.0** and `argsort` returns an essentially arbitrary order. Your top hit
is then meaningless rather than merely poor — exactly what `most-favored-nation`
produced.

## 8. Compared with

| | BM25 (sparse) | Dense (module 06) |
|---|---|---|
| Representation | ~30k dims, sparse | 384 dims, dense |
| Matching | exact terms, IDF-weighted | learned semantic proximity |
| Synonyms | ❌ | ✅ |
| Rare proper nouns | ✅ exact | ❌ blurred |
| Absent term | scores 0, no partial credit | approximates via sub-words |
| Training data | none | large paired corpora |
| Index | inverted index | HNSW graph |
| Explainability | ✅ point at the matching terms | ❌ opaque |
| Cost to add a document | update postings | one forward pass |
| Near-synonym discrimination | ❌ — measured 0.250 | ⚠️ 0.333–0.500 |

## 9. Interview angle

**"Why use BM25 in 2026 when we have embeddings?"** — Because they fail
differently. Dense retrieval blurs proper nouns and rare terms — it's trained for
semantic discrimination, and two company names occupy the same semantic role.
BM25 treats them as distinct tokens. On my eval, questions naming party entities
were exactly where dense retrieval struggled. The counterpoint from my own data:
BM25 lost overall (0.223 vs 0.363) and lost on near-miss traps too, so it earns
its place as a *complement*, not a replacement.

**"Explain BM25's two corrections over TF-IDF."** — Saturation and length
normalisation. Saturation, via `k₁`, makes the 20th mention of a term worth
almost nothing more than the 5th — the TF factor asymptotes to `k₁+1`. Length
normalisation, via `b`, penalises long documents that contain more of everything
by chance. Both are corrections for the fact that raw counts overstate relevance.

**"Where does BM25's 'intelligence' come from with no training?"** — IDF. It's
pure corpus statistics: a term appearing in 400 of 18,280 chunks carries ~250×
the weight of one appearing in 18,000. Nobody labels anything; the distribution
of the corpus tells you which words discriminate.

**"You predicted BM25 would help on near-miss questions. Did it?"** — No, and the
failure was instructive. It scored 0.250 against dense's 0.333 and 0.500. A
near-miss trap is legally *adjacent* language, so it shares nearly all its
vocabulary with the target clause — "cap on liability" versus "uncapped
liability". Lexical overlap is structurally unable to separate near-synonyms. The
cross-encoder fixed those cases at 0.917.

## 10. Test yourself

**Q1.** With `k₁ = 1.2`, compute the TF factor for `f = 1` and `f = 10`, ignoring
length normalisation. What does the comparison show?

<details><summary>Answer</summary>

`TF = f(k₁+1)/(f+k₁)`.

- `f=1`: `1·2.2/(1+1.2) = 2.2/2.2 = 1.00`
- `f=10`: `10·2.2/(10+1.2) = 22/11.2 = 1.96`

Ten times the occurrences buys **less than double** the score. The function
saturates toward `k₁+1 = 2.2`, encoding the judgement that a document mentioning
a term ten times is not ten times more about it. Raw TF would have returned 1 and
10.

</details>

**Q2.** Why does `most-favored-nation` score exactly 0.00 while `most favored
nation` scores 22.79 on the same corpus?

<details><summary>Answer</summary>

The tokeniser preserves hyphenated compounds, so `most-favored-nation` becomes a
**single token**. The corpus writes the concept unhyphenated, so that token
appears in zero documents — `n(q) = 0`, no document matches, every score is 0.

Unhyphenated, the query becomes three tokens (`most`, `favored`, `nation`), all
present, and BM25 sums their IDF-weighted contributions to 22.79.

The deeper point: BM25 has **no partial credit**. There is no notion of a token
being *close to* another token. This is the exact inverse of dense retrieval's
weakness, and why the two are complementary.

</details>

**Q3.** A query's terms appear in no document. What does BM25 return, and why is
that worse than returning nothing?

<details><summary>Answer</summary>

All scores are 0.0, so `argsort` returns k chunks in whatever order ties resolve —
effectively arbitrary. The API returns a normal-looking result set with k hits.

It's worse than returning nothing because **the caller cannot distinguish "here
are the best matches" from "I found nothing and these are arbitrary"**. Downstream
the LLM receives five irrelevant chunks presented as retrieved evidence.
Defensively: check whether `max(scores) == 0` and treat that as an explicit
no-match, or rely on hybrid fusion so the dense side still contributes signal.

</details>

**Q4.** IDF requires no training. Explain where its discriminative power comes
from, and give a case where IDF misleads.

<details><summary>Answer</summary>

It comes from the corpus's own term distribution: `ln((N−n+0.5)/(n+0.5)+1)`
rewards terms concentrated in few documents. Rarity within *this* corpus is a
proxy for informativeness, and it requires no labels.

**Where it misleads:** when rarity is an artifact rather than a signal.
- **Typos and OCR noise** are maximally rare, so they get maximal IDF. A query
  containing a typo that happens to appear in one garbled chunk will rank that
  chunk top.
- **Boilerplate that is rare corpus-wide but uninformative** — a filing agent's
  name appearing in three documents gets high IDF while carrying no relevance to
  any question.
- **Domain-uniform corpora invert the intuition:** in a corpus of only
  indemnification clauses, `indemnification` appears everywhere and gets near-zero
  IDF — the most topically central term becomes worthless for ranking.

</details>

**Q5.** Harder. BM25's `recall@50` doc-scoped is 0.9801 — essentially the same as
dense's 0.9789 — yet its `recall@5` is 0.411 versus dense's 0.575. What does that
pattern tell you, and what does it predict about fusing them?

<details><summary>Answer</summary>

The two retrievers **find the same things but order them differently**. Nearly
identical recall@50 means both pull the gold chunk into a 50-candidate pool with
equal reliability; the recall@5 gap means BM25's *ranking* within that pool is
substantially worse.

That decomposition matters for fusion. If you fuse by rank (module 09), BM25
contributes a noisier ordering over roughly the same candidate set — so the fused
top-5 can be *worse* than dense alone, while the fused candidate pool is at least
as good. Which is exactly what happened: hybrid recall@5 fell to 0.481 while
recall@50 rose to 0.987.

The prediction: **fusion helps the ceiling and hurts the top**, so it is only
worth it if you follow with a re-ranker that can exploit the better pool. That is
precisely the doc-scoped result in module 10 — hybrid plus cross-encoder reached
0.762, well above dense alone, even though hybrid *alone* was worse.

</details>
